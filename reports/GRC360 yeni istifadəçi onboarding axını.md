# GRC360 onboardingini təməl, checklist və importla qurun

GRC360-ın yeni müştəri üçün guide flow-u tək bir tutorial olmamalıdır. Bu, dörd qatlı bir sistemdir: **(1)** təşkilatı, ilk admini və standart məzmunu bir əməliyyatla yaradan provisioning; **(2)** adminə məcburi qısa bir setup wizard, ondan sonra isə server-də saxlanan, davam etdirilə bilən və canlı say göstəricilərindən hesablanan setup checklist; **(3)** əsas registrlər üçün template, sütun mapping, dry run və upsert dəstəkli data import; **(4)** "sistemlərinizi qoşun" addımı. Bu son addım dürüst olmalıdır: bu gün GRC360 yalnız LDAP, SMTP test və webhook təklif edə bilir. Hazırda **bu qatların heç biri işlək vəziyyətdə deyil**. `POST /api/v1/tenants` yalnız tenant sətri yaradır. İlk admin ancaq dev profili və ya əl ilə yazılmış SQL ilə yaranır. Dəvət linkinin açılacağı səhifə yoxdur. Assets, Vendors, Risks və Controls üzərindəki Import düyməsi həmişə uğursuz olan demo dialoqu açır. Məhsulda heç bir onboarding UI yoxdur. Rəqib compliance-automation alətləri (Drata, Secureframe, Vanta) eyni sıranı izləyir: təşkilat profili, sonra identity provider və inteqrasiyalar, sonra framework seçimi, control sahibləri, işçilər və siyasətlər. Hamısı progress göstərən checklist-i məhsulun içində saxlayır. Konfiqurasiya saatlar və ya günlər çəkir, tam "onboarded" vəziyyətinə isə 30–60 gündə çatılır. Empirik sübutlar uzun, avtomatik açılan tour-ların əleyhinədir. İşləyən yanaşma qısa, istifadəçinin özünün başlatdığı və real əməliyyata bağlı addımlardır. GRC360-ın ən böyük hazır aktivi isə dokumentasiyada koddan yoxlanmış **13 addımlıq setup sırasıdır**: bu, checklist-in hazır skeletidir. Tövsiyə olunan ardıcıllıq belədir: əvvəlcə Faza 0 blokerləri (provisioning, sign-in zamanı tenant-ın tapılması, invite və şifrə həyat dövrü, sınıq import dialoqu, RM-02), sonra checklist və wizard MVP, sonra import çərçivəsi və starter content, ən sonda SSO/SCIM və konnektorlar.

## Bu gün GRC360-da yeni müştəri ilk admin girişinə belə mühəndis olmadan çata bilmir

Ən ciddi boşluq UI-da deyil, ondan bir qat aşağıdadır. `TenantApplicationService.createTenant()` adı, planı və subdomain-i yoxlayır, branding tətbiq edə bilir və tenant-ı saxlayır, amma **heç bir istifadəçi, rol və ya seed data yaratmır** ([TenantApplicationService.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/application/tenant/TenantApplicationService.java)). Tenant API hər hansı tenant-ın ADMIN roluna açıqdır, yəni yalnız platforma operatoruna məhdudlaşdırılmayıb ([SecurityConfig.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/config/SecurityConfig.java)). Web client isə bu API-ni ümumiyyətlə çağırmır (known issue PD-01) ([known-issues.md](/home/user/grc_frontend_code/doc/guide/appendices/known-issues.md)). Tenant ilə giriş hesablarını birlikdə yaradan yeganə kod `@Profile("dev")` ilə işarələnmiş `DevDataInitializer`-dir. O, "Test Tenant" və `test@example.com` / `password123` hesabını yaradır ([DevDataInitializer.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/config/DevDataInitializer.java)). Dev profili olmadan təzə quraşdırmada nə tenant, nə istifadəçi olur. Dokumentasiya iki yol təklif edir: dev profili ilə bir dəfə işə salmaq və ya SQL ilə sətir əlavə etmək. Bu problem PD-12 kimi qeyd olunub ([02-installation-and-deployment.md](/home/user/grc_frontend_code/doc/guide/05-technical/02-installation-and-deployment.md)).

Seed məntiqi də təsadüfi işləyir. Daxili Admin, Read Only və Third Party qrupları server açılarkən **yalnız artıq istifadəçisi olan tenant-lar üçün** sinxronlaşdırılır ([PermissionCatalogSyncRunner.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/organization/seed/PermissionCatalogSyncRunner.java)). Deməli, API ilə yaradılmış yeni tenant-da kimsə `/permissions/seed` çağırana və ya server yenidən başlayana qədər Admin qrupu olmur. Risk parametrləri ilk oxunuşda "lazy" şəkildə yaranır: 5×5 likelihood/impact şkalası və `numericalAppetite=50.0` ([RiskSettingsServiceImpl.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/risk/service/impl/RiskSettingsServiceImpl.java)). 5×5 şkalada maksimum bal 25-dir, ona görə **"Above Appetite" vəziyyəti heç vaxt baş verə bilməz** (RM-02) ([known-issues.md](/home/user/grc_frontend_code/doc/guide/appendices/known-issues.md)). Məhsulda framework mətni yoxdur, hər framework boş compliance package kimi yaradılır. Standart incident stage-lər də yoxdur ([03-first-time-setup.md](/home/user/grc_frontend_code/doc/guide/01-getting-started/03-first-time-setup.md)).

Multi-tenant SaaS üçün ikinci bloker sign-in zamanı tenant-ın necə tapılmasıdır. Login sorğusu `X-Tenant-Id` header-i tələb edir. FE bu dəyəri `localStorage`-dan və ya build zamanı verilən `NEXT_PUBLIC_TENANT_ID`-dən götürür ([apiClient.ts](/home/user/grc_frontend_code/src/shared/api/apiClient.ts)). Tenant seçimi və ya təşkilat slug-ı ilə giriş yoxdur. Subdomain həlli BFF arxasında işləmir, çünki proxy `Host`-u silir (PD-13) ([01-architecture.md](/home/user/grc_frontend_code/doc/guide/05-technical/01-architecture.md)). Nəticədə eyni FE-də ikinci müştərinin istifadəçiləri təzə brauzerdən daxil ola bilmir. Plan limitləri də (BASIC 10 istifadəçi, PROFESSIONAL 50, ENTERPRISE 200) təyin olunub, amma `validateTenantLimits` heç yerdə çağırılmır ([TenantApplicationService.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/application/tenant/TenantApplicationService.java)).

### Dəvət olunan istifadəçinin yolu ortada qırılır

Backend-də dəvət mexanizmi var: `POST /api/v1/users/invite` `UserInvite` yaradır və `/invite/{token}` linkini e-poçtla göndərir. Lakin dəvət **yalnız e-poçt ünvanını** daşıyır: ad, qrup və ya departament yoxdur. FE-də `/invite` səhifəsi yoxdur. Token-i qəbul edən endpoint də yoxdur: `validateInviteToken` mövcuddur, amma onu heç nə çağırmır, `used=true` isə heç vaxt təyin olunmur ([AuthServiceImpl.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/auth/service/impl/AuthServiceImpl.java)). Forgot/reset password, öz şifrəsini dəyişmə və self-registration yoxdur. `TenantContextFilter` `/onboarding`, `/register`, `/forgot-password` və `/reset-password` yollarını tenant həllindən azad edir, amma bu yollar üçün controller yazılmayıb ([TenantContextFilter.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/infrastructure/tenancy/TenantContextFilter.java)). MFA da sınıqdır: `/mfa/enable` göndərilən TOTP kodunu secret kimi saxlayır, `/mfa/verify` isə kodu yoxlamır ([MfaController.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/settings/api/MfaController.java)). Bu gün admin istifadəçini formada və ya CSV ilə şifrə ilə yaradır və şifrəni kənar kanalla ötürür.

### Onboarding UI-ın heç bir elementi yoxdur, amma onun skeleti dokumentasiyada hazırdır

FE-də onboard, wizard, joyride, shepherd, welcome, getting started, first login və checklist sözləri ilə axtarış heç bir onboarding funksiyası tapmadı. Asılılıqlar arasında tour, wizard və ya analytics kitabxanası da yoxdur ([package.json](/home/user/grc_frontend_code/package.json)). Girişdən sonra hər kəs `/command-center`-ə yönləndirilir ([login/page.tsx](</home/user/grc_frontend_code/src/app/(public)/login/page.tsx>)). Dashboard icazəsi olmayan istifadəçi isə "Access Denied" görür (PW-11). `User` entity-sində first-login və ya onboarding statusu sahəsi yoxdur. İlk girişi aşkarlamaq üçün istifadə oluna biləcək yeganə siqnal `lastLoginAt`-dır ([User.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/organization/entity/User.java)). Boş vəziyyətlərin çoxu sadəcə "No records found." göstərir. Dəstək bölməsi əvvəlcədən doldurulmuş bir `mailto:` linkindən ibarətdir. Onboarding progress-ini saxlamaq üçün server tərəfdə ümumi tenant və ya user settings cədvəli də yoxdur, `localStorage`-da isə yalnız tema, dil və sessiya açarları saxlanır ([settings/entity](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/settings/entity)).

Buna qarşı GRC360-ın güclü tərəfi var. `03-first-time-setup.md` record asılılıqlarına görə sıralanmış **13 addım** təyin edir: (1) platforma parametrləri, (2) departamentlər, (3) qruplar və icazələr, (4) istifadəçilər, (5) coverage və objectives, (6) vendorlar və müqavilələr, (7) aktivlər və data flow-lar, (8) risk şkalası və appetite, (9) compliance package-lər, (10) siyasətlər, controllar və continuity planlar, (11) risklər və istisnalar, (12) compliance analysis, (13) layihələr və incident stage-lər. Hər addım hansı səhifədə edildiyini göstərir ([03-first-time-setup.md](/home/user/grc_frontend_code/doc/guide/01-getting-started/03-first-time-setup.md)). Nümunə data üçün də xammal var. Sənəd branch-ındakı `seed_demo.py` API vasitəsilə bir-biri ilə bağlı demo zənciri yaradır: asset → risk → control → policy → compliance item → project ([seed_demo.py](/home/user/grc_frontend_code/doc/guide/tools/seed_demo.py)). Settings › Clear Data isə tenant datasını silə bilir ([TenantDataResetServiceImpl.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/settings/service/impl/TenantDataResetServiceImpl.java)). Hər ikisi hələ məhsula çevrilməyib.

Bir xəbərdarlıq da var: guide flow müştərini bəzi səhifələrə yönləndirəcək, amma o səhifələrdə məlum data xətaları var. Bunlar RM-02, OH-01 (qrup seçmək istifadəçinin bütün qruplarını əvəz edir), OH-07 (Clone Group işləmir), CH-01 (riski saxlamaq compliance verdict-lərini üstələyir) və GH-11-dir (objective-i redaktə etmək datanı silir) ([known-issues.md](/home/user/grc_frontend_code/doc/guide/appendices/known-issues.md)). Bu səhifələrə yönləndirən checklist addımları bu xətalar düzəlməmiş buraxılmamalıdır.

## Rəqiblər eyni sırada qurur: profil, identity, framework, sahiblər, işçilər

Compliance-automation alətləri demək olar eyni sxemi tətbiq edir. **Drata**-nın Quick Start-ı yalnız adminlər üçün olan, bir oturumda bitirilməsi vacib olmayan bir checklist-dir. Bölmələr bu sıradadır: əsas təşkilat məlumatları; IdP, sonra cloud, version control və ticketing bağlantıları; framework scoping və control sahiblərinin təyini; işçilərin compliance-i; Policy Center. Sonda "What's Next" siyahısı gəlir. Klassik versiya ilkin şərti çatmayan addımları kilid ikonu ilə göstərir və isteğe bağlı addımları ötürməyə imkan verir ([Drata Quick Start](https://help.drata.com/en/articles/13265650-quick-start-guide-new-experience); [Drata classic](https://help.drata.com/en/articles/12004296-quick-start-guide)). IdP bağlantısı ilk gəlir, çünki "Drata uses your identity provider to establish your personnel list" və rollar da IdP olmadan təyin edilə bilmir ([Drata Quick Start](https://help.drata.com/en/articles/13265650-quick-start-guide)).

**Secureframe** onboarding-i üç fazaya bölür: hesab və giriş, inteqrasiyalar və proqramın qurulması, operativləşdirmə və audit hazırlığı. "Onboarded" anlayışını konkret milestone-larla təyin edir: işçilər dəvət olunub və scope-a görə kateqoriyalaşdırılıb, siyasətlər dərc olunub, ən azı 1–2 inteqrasiya sinxronlaşır, **vendor siyahısı və risk reyestri doldurulub**, control sahibləri təyin olunub. Göstərdiyi müddətlər: ilkin setup 1–3 gün, ümumi **30–60 gün**, rekord isə 7 gündən az ([Secureframe onboarding overview](https://support.secureframe.com/en/articles/15111050-secureframe-onboarding-overview-roles-milestones-and-best-practices)). **Vanta**-nın Compliance Roadmap-i profil menyusundan açılır, tamamlandıqdan **3 gün sonra özü gizlənir**, amma yenidən açıla bilər. "?" menyusu Help Center, Community və Live Training-ə aparır ([Vanta Getting Started Resources](https://help.vanta.com/en/articles/11345375-getting-started-resources-in-vanta)). Vanta-da Sandbox Mode və "Bringing your Current Compliance Program into Vanta" bələdçisi də var ([Vanta Getting Started Guides](https://help.vanta.com/en/collections/12575234-getting-started-guides)). Implementation planı 30-60-90 gün ritmi ilə gedir: 30-cu gün planlama, 60-cı gün əsas qurulum, 90-cı gün audit hazırlığı ([Vanta GRC Implementation Guide](https://help.vanta.com/en/articles/11488007-vanta-grc-implementation-guide)). Sprinto əsas konfiqurasiyanın "bir neçə saat" çəkdiyini deyir ([Sprinto FAQ](https://docs.sprinto.com/frequently-asked-questions-faqs)).

Enterprise IRM platformalarında self-serve ilk açılış demək olar ki, yoxdur. Onları istifadəçilər gəlməmişdən əvvəl professional services komandası konfiqurasiya edir. AuditBoard-un SOW-u Initiation, Discovery, Design, Configure və Test fazalarından ibarətdir və hər faza 1–4 həftə çəkir ([AuditBoard SOW](https://optro.ai/download/agreements/implementation/archive/AuditBoard-Implementation-Services-Module-Upgrade-02262025.pdf)). LogicGate paketləri hər Application üçün **30–150 gün** çəkir ([LogicGate services](https://www.logicgate.ai/services-description)). ServiceNow-un ilk modulu partnyor qiymətləndirməsinə görə 8–16 həftədir ([BDEMerson](https://www.bdemerson.com/service/servicenow-grc-implementation)). Open-source tərəfdə SimpleRisk altı addımlı quraşdırma wizard-ı təklif edir: DB, konfiqurasiya, admin hesabı və ilkin reference data ([SimpleRisk wizard](https://support.simplerisk.com/kb/01-05-the-initial-configuration-wizard)). Sonrası isə boş tətbiqdir. Eramba forumunda istifadəçi checklist tipli "get started" wizard və uydurma demo şirkət istədi, çünki "business unit-ləri map etdikdən sonra nə edəcəyini bilmirdi". Eramba sənədləri "yuxarıdan aşağı oxumağı" tövsiyə etdi və mövzuda wizard qurulduğuna dair heç bir iz yoxdur ([Eramba forum](https://discussions.eramba.org/t/question-missing-step-by-step-wizard-to-start/1170)). GRC360 da Eramba kimi geniş, çox modullu bir məhsuldur, buna görə bu səhvi təkrarlamamalıdır.

Qeyri-admin istifadəçilər rəqib məhsullarda tur ilə deyil, **dəvət və təyin olunmuş tapşırıqlar** vasitəsilə onboard olunur. Secureframe-in işçilər üçün ayrıca bələdçisi var ([Secureframe employee guide](https://support.secureframe.com/en/articles/15900492-completing-employee-onboarding-employee-guide)). Vanta sahibləri hub-lar üzrə təyin edir, testlər uğursuz olanda onlara bildiriş göndərir və auditora ayrıca "Auditor" icazəsi verir ([Vanta GRC Implementation Guide](https://help.vanta.com/en/articles/11488007-vanta-grc-implementation-guide)). Hyperproof-da dəvət olunan istifadəçi dəvəti **qəbul etməyənə qədər ona obyekt təyin etmək olmur**, kütləvi onboarding isə Okta ilə SCIM üzərindən gedir ([Hyperproof docs](https://docs.hyperproof.io/cm/en/get-to-know-hyperproof/manage-users/adding-users-to-your-organization)). GRC360-da bu da yoxdur: register-də owner və ya assignee kimi təyin olunan şəxsə bildiriş getmir. Yeganə istisna Continuity Plan-dakı Awareness Role-dur ([notifications-and-jobs.md](/home/user/grc_frontend_code/doc/guide/appendices/notifications-and-jobs.md)).

### Uzun tour-lar işləmir, qısa və istifadəçinin özünün başlatdığı addımlar işləyir

NN/g-nin 70 iştirakçılı tədqiqatında tutorial tapşırıq uğurunu artırmadı (91% və 94%, fərq əhəmiyyətsizdir). Üstəlik tapşırıqlar **daha çətin hiss olundu** (SEQ 4.92 və 5.49, p=0.047) ([NN/g](https://www.nngroup.com/articles/mobile-tutorials/)). Bu tədqiqat mobil tətbiqlərdə aparılıb, B2B üçün birbaşa sübut deyil, amma istiqaməti aydındır. Chameleon-un 550M+ qarşılıqlı əlaqəsi üzrə 2025 hesabatına görə 5 addımdan uzun tour-lar istifadəçilərin yarıdan çoxunu itirir. Launcher və ya checklist-dən açılan tour-lar **67%**, digərləri isə 31% tamamlanır. Səhifə açılarkən avtomatik göstərilən modal-ların tamamlanma nisbəti ən aşağıdır (39%). Progress indikatoru tamamlanmanı təxminən 12% artırır ([Chameleon Benchmark 2025](https://chameleon.io/benchmark-report)). Checklist-lər də sehrli həll deyil: Userpilot-un 188 şirkət üzrə məlumatında orta tamamlanma **19.2%, median 10.1%**-dir ([Userpilot benchmark](https://userpilot.com/saas-product-metrics/)). Hər iki mənbə vendor datasıdır, yalnız istiqamət göstərir. Buradan çıxan nəticə: checklist qısa, rola görə fərdi və real record-larla avtomatik tamamlanan olmalıdır, aktivasiyanın yeganə vasitəsi də olmamalıdır.

## Data importu GRC360 onboardingində ən zəif halqadır

Müştərinin mövcud risk reyestrini, aktiv inventarını, vendor siyahısını və ya control kitabxanasını bu gün UI vasitəsilə köçürmək **mümkün deyil**. Paylaşılan grid hər Import kliki ilə "the import structure is not ready yet" toast-ı göstərir. Səhifə `onImportCsv` vermirsə, `CsvImportModal` `/api/v1/import-csv-demo` endpoint-i ilə açılır. `resolveUrl()` bu yolun əvvəlinə yenidən `/api/v1` əlavə edir və sorğu mövcud olmayan `/api/v1/api/v1/import-csv-demo` ünvanına gedir ([DataTable.tsx](/home/user/grc_frontend_code/src/shared/ui/DataTable.tsx); [apiClient.ts](/home/user/grc_frontend_code/src/shared/api/apiClient.ts)). Bu, Assets, Vendors, Departments, Controls, Policies və Risks səhifələrinə aiddir. UI-da 11 import işləyir: Users, Projects, Tasks, Expenses, Security Incidents, incident stage-lər, Package Items, Assessments, Obligations, Compliance Exceptions və Audit Findings. Backend-də isə controls, policies, policy exceptions, continuity plans və üç risk reyestri üçün import endpoint-ləri yazılıb, amma UI-a qoşulmayıb. Assets, data flows, vendors, service agreements, departments və groups üçün isə import ümumiyyətlə yoxdur ([grc_backend_code/modules](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules)).

Mövcud importların formatı da onboarding üçün yararsızdır. Əlaqələr daxili UUID-lərlə verilir: məsələn, control import-da `controloperatorcontactuserid` və `securitypolicyids` ([ControlCsvImportServiceImpl.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/control/service/impl/ControlCsvImportServiceImpl.java)). Users importu sətirləri `line.split(",")` ilə bölür, yəni dırnaqlı dəyərləri tanımır. Sətirlərin bir hissəsi uğursuz olsa belə həmişə "Users imported." göstərir ([UserServiceImpl.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/organization/service/impl/UserServiceImpl.java)). Risk import `successCount` və `errorCount` qaytarır, `CsvImportModal` isə `successRows` və `failedRows` gözləyir. Ona görə olduğu kimi qoşulsa, saylar boş görünəcək ([CsvImportModal.tsx](/home/user/grc_frontend_code/src/shared/ui/CsvImportModal.tsx)). Task export-u layihə adını verir, task import-u isə `project_id` UUID tələb edir, yəni export edilmiş fayl yenidən import oluna bilmir (OC-02). XLSX dəstəyi yoxdur. Dokumentasiya müştəriyə qalan registrlər üçün "Strativu kontaktınızdan API ilə bulk load istəyin" deyir ([03-first-time-setup.md](/home/user/grc_frontend_code/doc/guide/01-getting-started/03-first-time-setup.md)). Integrations səhifəsindəki "20 registr üçün CSV dry run" kartı da həqiqəti şişirdir (PD-18) ([known-issues.md](/home/user/grc_frontend_code/doc/guide/appendices/known-issues.md)). Guide flow bu karta istinad etməzdən əvvəl kart düzəldilməlidir.

### Bazar dörd-beş addımlı import wizard-ında birləşib

Yeni nəsil GRC importerləri eyni nümunəni izləyir. **Drata**-da əvvəl field mapping, sonra enum sahələr üçün value mapping gəlir. Xətalı hüceyrələr qırmızı, xəbərdarlıqlar sarı olur, xəta düzələnə qədər Submit bağlı qalır. Sətir yeni record yaradır, yalnız Control Code mövcud bir code ilə üst-üstə düşəndə **"will be updated"** göstərilir və mövcud record yenilənir ([Drata bulk import](https://help.drata.com/en/articles/13381439-import-or-update-controls-in-bulk-new-experience)). **Vanta**-nın risk importunda tək məcburi sütun "Risk Scenario"-dur. Yeniləmə round-trip ilə gedir: export, redaktə, Risk ID ilə yenidən upload ([Vanta risks](https://help.vanta.com/en/articles/12005142-adding-and-managing-risks)). Vanta mövcud proqramı olan müştəri üçün iş həcmini də açıq yazır: custom controllar **5–7 saat**, custom framework 3–5 saat, testlərin control-lara map edilməsi 10–20 saat ([Vanta: bringing your program](https://help.vanta.com/en/articles/11345361-bringing-your-current-compliance-program-into-vanta)). **Secureframe** risk reyestrini "olduğu kimi" qəbul edir. İstifadəçi header sətrini seçir və sütunları map edir, import edilən risklər isə **Draft** statusu alır ([Secureframe flexible CSV](https://support.secureframe.com/en/articles/15111225-risk-register-flexible-csv-uploads)). Secureframe bu importer-ə keçməzdən əvvəl import xətaları "import error on line 62" kimi qeyri-müəyyən idi və tiketlər mühəndisliyə eskalasiya olunurdu. Keçiddən sonra, öz dediyinə görə, yüzlərlə e-poçtun yerinə bir ildə bir neçə tiket qalıb. Bu, vendor case study-sidir ([OneSchema case study](https://oneschema.co/case-studies/accelerate-upmarket-product-roadmap)). Bunun əksi Eramba-dır: upsert açarı yoxdur, "eyni CSV-ni iki dəfə import etsəniz, data dublikat olacaq", əlaqələr üçün isə rəqəmli ID tələb olunur ([Eramba CSV imports](https://eramba.org/learning/courses/37)).

Bu nümunələrdən GRC360 üçün üç qayda çıxır. Birincisi, hər entity üçün müştərinin idarə etdiyi **oxunaqlı bir business key** olmalıdır: Control Code, Risk ID, Asset tag və s. Import da create/update preview göstərməlidir. İkincisi, əlaqələr UUID ilə deyil, ad, e-poçt və ya kod ilə həll olunmalıdır. Bu, təbii bir import sırası yaradır: org və istifadəçilər, sonra framework və tələblər, sonra controllar, sonra aktivlər və vendorlar, sonra risklər, ən sonda findings. Üçüncüsü, rəylərdə adı çəkilən heç bir GRC vendor import-u geri qaytarmağı (rollback) sənədləşdirmir. Ona görə hər import **etiketlənmiş batch** kimi saxlanmalı, sonra tapılıb silinə bilməlidir ([SaaSUI import patterns](https://www.saasui.design/blog/saas-data-import-mapping-ux-patterns)). Bu batch qeydi eyni zamanda audit trail-dir. Siyasətlər sətir kimi import olunmur. Onlar DOCX/PDF kimi yüklənir və ya SharePoint/Confluence/Drive-dan sinxronlaşdırılır (Vanta).

Başqa GRC alətindən köçmək əslində yenidən implementasiya deməkdir. Control mapping-lər köçmür, köhnə evidence davamlı audit tarixçəsi kimi gəlmir, işçilər siyasətləri yenidən qəbul etməli olur. Tək framework-lu SaaS üçün bu iş **4–6 həftə** çəkir. Type II müşahidə dövrünün ortasında köçmək tövsiyə olunmur ([Agency migration guide](https://blog.getagency.com/articles/switching-drata-to-vanta-migration-guide); mənbə migration xidməti satır). Buradan GRC360 üçün aydın nəticə çıxır: importer Vanta, Drata, Eramba və SimpleRisk export-larını olduğu kimi qəbul etməli və mənbə alətə görə mapping preset-lərini saxlamalıdır. Onboarding wizard-ı isə "növbəti auditiniz nə vaxtdır?" sualını verməlidir.

### Boş framework yerinə hazır məzmun lazımdır

Rəqiblərdə framework seçimi məhsulun nə göstərəcəyini müəyyən edir: tələbləri, map olunmuş controlları, testləri, tələb olunan siyasətləri və readiness balını. Vanta 35-dən çox framework-dan danışır, SOC 2 üçün isə 15 policy template-i var ([Vanta policies](https://help.vanta.com/en/articles/11345363-getting-started-with-policies)). GRC360-da isə package formasında framework-a yeganə istinad "ISO 27001, PCI, Etc." placeholder mətnidir ([FrameworksPage.tsx](/home/user/grc_frontend_code/src/domain/compliance-hub/FrameworksPage.tsx)). Ən ucuz qanuni baza **Secure Controls Framework (SCF)**-dir: Creative Commons lisenziyalıdır, 1,500+ control 200+ qanun və framework-a map olunub, CSV/Excel və OSCAL JSON formatında yayılır, ildə 4 dəfə yenilənir ([SCF](https://securecontrolsframework.com/)). CISO Assistant versiyalaşdırılmış kitabxana formatı üçün açıq bir nümunə verir: Excel ilə YAML arasında çevrilmə, URN identifikatorları, version-gated yeniləmələr, eləcə də equal, subset, superset və intersect tipli mapping set-lər. ISO 27001 və CIS kimi yenidən yayılması qadağan olan məzmunu isə istifadəçi öz faylı ilə yükləyir ([CISO Assistant tools](https://github.com/intuitem/ciso-assistant-community/blob/main/tools/README.md)). Azərbaycan regulyasiyaları da həmin formatda custom kitabxana kimi əlavə oluna bilər. Bu, yerli bazarda əhəmiyyətli fərqləndirici üstünlükdür. Mövcud 8 sütunlu package-item import formatı ([csv-import-export.md](/home/user/grc_frontend_code/doc/guide/appendices/csv-import-export.md)) və lazy-default pattern-i (`ensureDefaults`) starter content paketlərini bağlamaq üçün hazır yerlərdir.

## "Sistemlərinizi qoşun" addımı bu gün yalnız üç şeyi dürüst vəd edə bilər

GRC360-da hazırda işləyən inteqrasiyalar bunlardır. **LDAP/AD** şifrə yoxlaması işləyir, amma yalnız GRC360-da artıq Active hesabı olan şəxslər üçün: JIT provisioning və qrup sinxronizasiyası yoxdur. **Webhook-lar** HMAC-SHA256 ilə imzalanır, amma retry və çatdırılma tarixçəsi yoxdur. **SMTP** yalnız mühit dəyişənləri ilə konfiqurasiya olunur və yalnız dəvət və test e-poçtu göndərir ([02-authentication-and-sso.md](/home/user/grc_frontend_code/doc/guide/04-administration/02-authentication-and-sso.md); [integrations-automation.md](/home/user/grc_frontend_code/doc/guide/02-modules/integrations-automation.md)). OAuth və SAML konnektorları saxlanılır, amma heç bir login axını onlardan istifadə etmir. Security chain yalnız JWT-dir, `oauth2Login` və ya `saml2Login` yoxdur ([SecurityConfig.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/config/SecurityConfig.java)). OAuth success endpoint-i hətta `"mock-jwt-token-for-e2e-testing"` qaytarır ([OAuthController.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/auth/api/OAuthController.java)). SCIM, API token, HRIS, cloud, Jira və verilənlər bazası konnektorları yoxdur. `apiAccessEnabled` sahəsini isə heç nə oxumur. Bundan başqa, Spring scheduling söndürülüb: 7 `@Scheduled` job işləmir, yalnız ayrıca qurulmuş `NotificationSweepScheduler` işləyir ([NotificationSweepScheduler.java](/home/user/grc_backend_code/src/main/java/com/strativu/grc360/modules/notification/service/NotificationSweepScheduler.java)). Bu o deməkdir ki, "setup yarımçıq qaldı" xatırlatmaları və ya planlaşdırılmış sinxronizasiya üçün əvvəlcə həmin pattern-dən istifadə etmək və ya scheduling-i yoxlanılmış şəkildə aktivləşdirmək lazımdır.

Rəqiblərin sırası asılılıqlara əsaslanır. Drata-da ilk addım IdP-dir, çünki işçi siyahısını və rolları o yaradır. Sonra cloud ("dozens of security controls" üçün evidence), sonra version control, sonra ticketing gəlir. HRIS isə yalnız zənginləşdirmə üçündür ([Drata Quick Start](https://help.drata.com/en/articles/13265650-quick-start-guide); [Drata HRIS](https://help.drata.com/en/articles/13344234-how-drata-uses-hris-data-new-experience)). Enterprise IRM-də başqa model işləyir. ServiceNow JDBC data source-ları və Integration Hub JDBC step-i on-prem MID Server üzərindən işlədir və icazəli SQL əməliyyatlarını property ilə məhdudlaşdırır ([ServiceNow JDBC step](https://www.servicenow.com/docs/r/integrate-applications/integration-hub/jdbc-step.html)). Archer-in SaaS versiyasında daxili sistemlərə çatmaq üçün "daxildə server qurmaq lazımdır" ([Archer community](https://isyzh67588.lithium.com/t5/archer-custom-objects-forum/trigger-datafeed-using-custom-object-button/m-p/716244)). Firewall arxasındakı sistemlər üçün sənaye nümunəsi yalnız xaricə qoşulan agent-dir: port 443 üzərindən, mutual TLS ilə, inbound port açmadan ([Workato on-prem](https://docs.workato.com/on-prem.html)). GRC360 həm SaaS, həm on-prem işlədiyi üçün on-prem quraşdırmada agent lazım deyil: GRC360 serveri birbaşa read-only DB istifadəçisi ilə müştərinin view-larına JDBC ilə qoşula bilər.

Təhlükəsizlik tərəfində qaydalar aydındır və auditorların gözləntiləri ilə üst-üstə düşür. OWASP secret-ləri mərkəzləşdirməyi, envelope encryption tətbiq etməyi ("keys next to the secrets" saxlamamağı), rotation-u avtomatlaşdırmağı və hər secret girişini dəyişdirilə bilməyən audit log-a yazmağı tövsiyə edir ([OWASP Secrets Management](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)). AWS cross-account bağlantısında hər tenant üçün **vendor tərəfindən yaradılan unikal external ID** confused-deputy hücumunun qarşısını alır ([AWS IAM](https://docs.aws.amazon.com/IAM/latest/UserGuide/confused-deputy.html)). Datadog əlavə olaraq rolun external ID-ni həqiqətən tələb etdiyini backend-də yoxlamağı və eyni AWS hesabının iki tenant-a bağlanmasını bloklamağı tövsiyə edir ([Datadog Security Labs](https://securitylabs.datadoghq.com/articles/securely-integrating-with-customers-aws-accounts/)). Build-vs-buy sualında unified API-lər (Merge və s.) hər linked account üçün qiymətləndirilir və uzun quyruqda boşluqlar qoyur. Sprinto-nun müştərisinin HRIS-i ilk provayderdə yox idi və Sprinto ikinci provayderə keçməli oldu ([Truto blog](https://www.truto.one/blog/why-sprinto-opted-for-truto-despite-already-using-a-leading-unified-api); promo mənbədir). On-prem müştərilər isə datanı üçüncü tərəf SaaS-dan keçirə bilmir. Buna görə IdP, cloud, Jira və ümumi JDBC/CSV/REST feed native qurulmalıdır. Xarici xidmət yalnız HRIS-in uzun quyruğu üçün nəzərdən keçirilə bilər.

### Wizard yalnız bir dəfəlik qərarlar üçündür, qalanı checklist-ə aiddir

Bloklayan wizard yalnız tenant adminin bir dəfə verməli olduğu qərarları əhatə etməlidir: təşkilat profili, dil (EN/AZ), scope-dakı framework-lar və starter content seçimi, risk metodologiyasının təsdiqi (işlək appetite ilə) və ilk həmkarların qrup və departamentlə dəvəti. Qalan hər şey davamlı checklist-ə keçməlidir. Bu checklist 13 addımlıq sənəd sırasının sıxlaşdırılmış variantıdır və record asılılıqlarına görə sıralanır. Drata kimi ilkin şərti çatmayan addımlar kilidli, isteğe bağlı addımlar isə ötürülə bilən göstərilir. Vanta kimi checklist tamamlandıqdan sonra gizlənir, amma help menyusundan yenidən açılır. Progress-in çoxu canlı saylardan hesablanmalıdır: departament > 0, istifadəçi > 1, package > 0, SMTP konfiqurasiya olunub, LDAP aktivdir və s. Server-də yalnız "dismissed" və "acknowledged" bayraqlarını saxlamaq qalır. Hər checklist addımı başqa həmkara təyin edilə bilməlidir, və bu, adi GRC360 tapşırığı və bildirişi yaratmalıdır. Admin-only addımlar FE-dəki substring yoxlamasına deyil, server-in admin müəyyənləşdirməsinə əsaslanmalıdır. Hazırda FE "IT Admins" adlı qrupu da admin sayır ([AuthContext.tsx](/home/user/grc_frontend_code/src/shared/auth/AuthContext.tsx)).

Yeni istifadəçilər üçün tutorial rola görə dörd yoldan ibarət olmalıdır. Hər yol eyni icazə dəstindən hesablanmalıdır ki, tour heç vaxt istifadəçinin görmədiyi moduldakı elementi hədəfləməsin. **Tenant admin** wizard və tam checklist alır. **Modul sahibi** (risk owner, third-party manager) "vendor siyahınızı import edin", "ilk qiymətləndirməni aparın" kimi modul checklist-i alır. **Contributor** 2–3 addım alır: "sizə təyin olunanlar", evidence necə təqdim olunur, bildiriş parametrləri. **Auditor/read-only** istifadəçi isə harada evidence, hesabat və export tapacağını görür və yaratma CTA-ları ona göstərilmir. Dəvət olunan istifadəçi wizard-ı ümumiyyətlə görməməlidir. Onun landing səhifəsi kimin dəvət etdiyini və ona nəyin təyin olunduğunu göstərməlidir. Bunun üçün təyinat bildirişləri və `UserInvite`-a ad, qrup və departament sahələri əlavə edilməlidir. Bu, Salesforce In-App Guidance-ın profil və icazəyə görə hədəfləmə prinsipi ilə uyğundur ([Salesforce Ben](https://www.salesforceben.com/salesforce-in-app-guidance/)).

### Importer: template, mapping, dry run, upsert, batch

Vahid import axını yeddi addımdan ibarət olmalıdır. Əvvəlcə istifadəçi entity-ni seçir və ipucu sətri və dropdown siyahıları olan XLSX template-i endirir. Sonra CSV və ya XLSX faylı yükləyir, sheet-i və header sətrini seçir. Üçüncü addım mənbə alətə görə preset-lərlə fuzzy sütun mapping-dir, dördüncüsü likelihood, impact və status kimi enum sahələr üçün value mapping-dir. Beşinci addımda hüceyrə səviyyəsində xəta və xəbərdarlıqları göstərən, "update existing (matched on key X)" sətirlərini vurğulayan grid gəlir. Altıncı addım created/updated/skipped/errored xülasəsi ilə async commit-dir. Yeddinci addımda import tarixçədə batch kimi qalır, xətalı sətirlər endirilə bilir və "bu batch-i sil" əməliyyatı mövcuddur.

Prioritet sırası müştəri dəyərinə və asılılıqlara görə müəyyən olunur: departamentlər, sonra qruplarla istifadəçilər (Users importuna dırnaq dəstəyi və nəticə hesabatı əlavə olunmaqla), aktivlər, vendorlar və müqavilələr, framework package-ləri və maddələri, controllar və risklər (hər ikisi backend-də var, sadəcə UI-a qoşulmalıdır), ən sonda isə sənəd yükləmə ilə siyasətlər.

Bütün importlar admin icazəsi arxasında olmalıdır. Hər import audit hadisəsi kimi loglanmalıdır: kim, nə vaxt, faylın hash-i, istifadə olunan mapping və saylar. Staging faylları qısa müddət saxlanmalıdır, nümunə olaraq ServiceNow-un 7 günlük defolt saxlama müddətinə baxmaq olar ([ServiceNow import sets](https://www.servicenow.com/docs/r/yokohama/integrate-applications/system-import-sets/c_ImportSetsKeyConcepts.html)). Hazır embeddable importer (OneSchema, Flatfile) sürət qazandırır, amma yeni sub-processor və data residency sualı yaradır. Bu, regional və on-prem müştərilər üçün ciddi məsələdir. Ona görə default yol react-spreadsheet-import və ya SheetJS kimi açıq kitabxanalar üstündə öz backend-imizdə qurmaqdır. Bu, qeydlərə əsaslanan nəticədir. Ölçülmüş müqayisə deyil.

### Alətlər: öz state store-umuz və MIT lisenziyalı tour renderer

GRC360 qapalı kodlu kommersiya məhsuludur. Shepherd.js və Intro.js AGPL-3.0 lisenziyalıdır və kommersiya lisenziyası tələb edir. **react-joyride 3.2.0** (MIT, React 19-u açıq dəstəkləyir, SSR-safe) və **driver.js 1.9.0** (MIT, asılılıqsız) isə təhlükəsiz seçimlərdir ([npm react-joyride](https://www.npmjs.com/package/react-joyride); [npm driver.js](https://www.npmjs.com/package/driver.js); [Shepherd pricing](https://www.shepherdjs.dev/pricing)). Kommersiya DAP-ları (Appcues, Pendo, Userpilot və s.) risk, incident və vendor datası saxlayan tətbiqə üçüncü tərəf skripti yeridir. Bu, yeni sub-processor, CSP konflikti və data residency problemi deməkdir. Qeydlərdə yalnız Whatfix sənədləşdirilmiş, internetdən tam ayrılmış on-prem rejimi təklif edir ([Whatfix](https://support.whatfix.com/docs/what-is-the-difference-between-self-hosted-and-on-premise-deployment-models)). Ona görə tövsiyə olunan arxitektura belədir: backend-də versiyalaşdırılmış və rola hədəflənmiş flow və checklist tərifləri, per-user və per-tenant state, FE-də isə bir dəfə state yükləyən provider, MIT tour renderer, shell-də checklist/launcher widget-i və checklist addımlarına bağlı empty-state komponentləri. Bütün mətnlər `az.ts` lüğətinə düşməlidir. FE tərcüməsi DOM-u yenidən yazan lüğətlə işləyir, server mətnləri isə ingiliscə qalır. Ona görə dəvət, xoş gəldin və xatırlatma e-poçtları üçün istifadəçinin dili server tərəfdə saxlanmalıdır ([az.ts](/home/user/grc_frontend_code/src/shared/i18n/az.ts)). Tour-lar WAI-ARIA dialog pattern-inə uymalıdır: fokus tələsi, Esc ilə bağlanma, fokusun geri qayıtması, avtomatik keçidin olmaması. Tour heç vaxt tapşırığı öyrənməyin yeganə yolu olmamalıdır.

Nümunə data barədə ehtiyatlı olmaq lazımdır. Compliance məhsulunda tenant içindəki nümunə record-lar audit evidence-i və hesabatları çirkləndirə bilər. Ona görə ya ayrıca demo/sandbox tenant (Vanta-nın Sandbox Mode-u kimi), ya da `is_sample` bayrağı ilə işarələnmiş, "Sample" nişanı daşıyan, hesabat, export və Trust Center-dən çıxarılan və bir kliklə silinən record-lar seçilməlidir. Bu mexanikanı sənədləşdirən mənbə tapılmadı, bu bir dizayn nəticəsidir.

### Ölçmə: öz baseline-ımızı qurmaq

FE-də heç bir telemetriya yoxdur, ona görə istifadəçilərin harada ilişdiyinə dair sübut da yoxdur. Ölçülməli ilk göstərici **rola görə aktivasiyadır**, ilk girişdən sonrakı 14 və 30 gün ərzində. Admin üçün bu, məsələn, framework-un seçilməsi, N risk və ya control yaradılması və ən azı bir həmkarın dəvət olunması deməkdir. Bunun yanında **TTV** (tenant yaradılandan ilk mənalı artefakta qədər keçən vaxt), hər addım üzrə başlanıb-bitmə saylarını müqayisə edən **checklist funnel-i**, tour-ların başladılma, tamamlanma və ötürülmə göstəriciləri, eləcə də **dəvət olunan və aktiv olan seat-ların nisbəti** izlənməlidir. Xarici benchmark-lar çox kobud istiqamət verir. Userpilot-da FinTech və Insurance kateqoriyasında aktivasiya cəmi 5%-dir, sales-led şirkətlərdə isə 41.6% ([Userpilot](https://userpilot.com/saas-product-metrics/)). Hədəflər GRC360-ın öz baseline-ından qoyulmalıdır. Həmin data CSM üçün tenant üzrə setup progress görünüşünü də qidalandırır.

## Nəticə

Əsas nəticə budur: GRC360-ın onboarding problemi UX problemi deyil. **Sahibsiz qalmış ilkin şərtlər problemidir**. Tenant provisioning, tenant-ın tapılması, dəvət və şifrə həyat dövrü, import müqaviləsi kimi infrastruktur boşluqları bağlanmasa, ən yaxşı tour və checklist belə müştərini SQL skriptinə və ya "Strativu kontaktınıza yazın" cümləsinə aparacaq. Buna görə ilk sprintlərdə ölçüləcək KPI "tour completion" yox, **"yeni tenant mühəndis müdaxiləsi olmadan neçə dəqiqəyə ilk admin girişinə və ilk import edilmiş reyestrə çatır"** olmalıdır. Digər tərəfdən, GRC360 sıfırdan başlamır. 13 addımlıq sırada asılılıqlar artıq düşünülüb, backend-də 10 qoşulmamış import, `dryRun` pattern-i, lazy-default mexanizmi, `seed_demo.py` və Clear Data var. Ona görə MVP-nin böyük hissəsi yeni domain modeli yaratmaq deyil, mövcud hissələri birləşdirib məhsula çevirməkdir.

İkinci nəticə rəqabətlə bağlıdır. Rəqiblər əsasən checklist UX-i ilə fərqlənmir, **hazır məzmun və inteqrasiya ilə** fərqlənir: framework seçimi tələbləri, controlları və siyasətləri avtomatik doldurur, IdP isə işçi siyahısını özü yaradır. GRC360-ın burada iki real fərqləndirici şansı var. Birincisi, SCF əsaslı kitabxananın üstündə Azərbaycan regulyasiyaları üçün hazır paketlər. İkincisi, həm SaaS, həm on-prem müştəriyə eyni şəkildə xidmət edən özümüzün qurduğu (üçüncü tərəf DAP və importer olmadan) onboarding və import qatı. Bu qat regulyasiya olunan müştərinin data residency sualına "data heç yerə getmir" cavabını verir. Açıq qalan suallar bunlardır: production topologiyası (bir paylaşılan instance, yoxsa hər müştəriyə ayrıca instance) koddan müəyyən olunmur; Vanta Roadmap-in daxili addımları açıq deyil; benchmark-ların hamısı vendor datasıdır; iş həcmi qiymətləndirilməyib. Bunlardan birincisi, yəni production topologiyası, Faza 0-ın dizaynını birbaşa müəyyən etdiyi üçün (provisioning və login zamanı tenant-ın tapılması) komanda daxilində Faza 0 başlamazdan əvvəl cavablandırılmalıdır.
